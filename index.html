Assistente multiagente com RAG

Uma pergunta, vários especialistas. Quem deve responder?

O problema

Numa empresa, a informação fica espalhada: os números estão em planilhas de finanças, as regras estão em documentos de políticas e as reclamações estão na ouvidoria. Quem pergunta não sabe onde olhar. E um chatbot genérico pode inventar um número que parece certo.

O desafio era construir um assistente que descobre sozinho de que assunto é a pergunta, responde só com base nos dados da empresa e mostra de onde tirou a resposta.

Como funciona, passo a passo

  1. A pergunta chega ao orquestrador. Um modelo de linguagem classifica o assunto (finanças, informações internas ou ouvidoria) e diz com que nível de confiança. "Como solicito férias?" vai para informações internas.
  2. Se a confiança é baixa, ele pergunta de volta. Em vez de chutar um agente, pede mais detalhes. "Preciso de uma informação" faz o sistema pedir esclarecimento.
  3. Cada agente responde do jeito certo para o seu tipo de dado. No financeiro, o modelo só preenche uma consulta estruturada e o código faz a conta. Nas informações internas, ele busca por significado (isso é o RAG: recuperar os trechos mais parecidos das 10 políticas e do FAQ e responder citando a fonte). Na ouvidoria, a busca é exata, por número de protocolo, com filtros e contagens. "Quanto foi gasto em despesas pagas de janeiro a março de 2025?" resulta em R$ 305.937,01, calculado pelo código.
  4. Antes de mostrar, o sistema confere. Se o texto escrito pelo modelo não bate com os números calculados, o código troca por um texto padrão. Protocolo que não existe? Ele diz que não encontrou, não inventa. "Existe o protocolo OUV-9999?" resulta em "não encontrado". "Me diga a senha de outro colaborador" é recusado, citando as políticas de segurança.
  5. A resposta mostra de onde veio. Cada resposta traz o assunto, o agente, a confiança, a tabela com os valores calculados, as fontes e um trace_id que liga a resposta à sua linha no log.

O que eu fiz

Desenvolvi o sistema todo: a API em FastAPI, a interface em HTML, CSS e JavaScript puros, o orquestrador, os três agentes, a camada que isola o provedor de LLM (com um cliente falso para os testes), o log de cada pergunta e a execução em Docker.

Documentei a arquitetura, as limitações conhecidas e o registro do desenvolvimento com IA (prompts, decisões, problemas e testes), como o desafio pedia.

NEXO: conversar com seus dados

O modelo entende o pedido. Quem faz a conta é o código.

O problema

Muita gente tem uma planilha cheia de dados e não sabe programar nem usar ferramentas de análise. Perguntar a um chatbot é fácil, mas modelos de linguagem erram contas. O NEXO deixa a pessoa enviar um CSV ou Excel e analisar os dados em português, com resultados em que dá para confiar.

Como funciona, passo a passo

  1. Você envia a planilha e faz uma pergunta em português. "Qual a média de vendas por região?"
  2. Um orquestrador decide quais agentes chamar. São três: o de dados (entende a tabela), o de análise e o de visualização. O orquestrador é escrito em Python puro, sem frameworks de agentes.
  3. O modelo só interpreta. Ele transforma o pedido numa instrução estruturada, e essa instrução é validada por contratos: o que vier fora do formato é rejeitado.
  4. Ferramentas fazem o trabalho. O Pandas calcula e o Plotly desenha o gráfico. O mesmo pedido dá sempre o mesmo resultado, e nenhum código escrito pelo modelo é executado.
  5. O sistema explica o resultado e deixa você refinar. A conversa tem memória da sessão, então dá para pedir ajustes ("agora só o último trimestre"). Os modelos (Gemini ou Ollama, que roda local) ficam atrás de uma interface comum e podem ser trocados.

O que eu fiz

Estou desenvolvendo o NEXO sozinho: o código dos agentes, do orquestrador e dos testes é todo meu.

MathClass: tutor de matemática

Um professor que entende a foto do caderno.

O problema

O projeto nasceu da minha experiência como professor: eu não consigo estar presente o tempo todo, e queria que o aluno tivesse ajuda com a matemática mesmo quando eu não estou por perto. Um tutor de IA serve se ele só fala de matemática, entende a conta que o aluno escreveu no caderno e explica no nível certo.

Como funciona, passo a passo

  1. O aluno escolhe o tipo de professor. O tutor explica passo a passo. O corretor explica rápido, para não perder tempo.
  2. Escreve a dúvida ou envia uma foto da conta no caderno. O modelo (Gemini 2.5 Flash) entende texto e imagem.
  3. O app monta a instrução completa. Junta as regras do professor escolhido, toda a conversa até ali (o histórico) e, por último, a foto. Assim a resposta faz sentido no contexto.
  4. O modelo só fala de matemática. A instrução manda recusar qualquer outro assunto, e a recusa tem humor. "Eu sou um professor de matemática, vc vai perder muita aura perguntando isso pra mim."
  5. Um botão limpa a conversa para o aluno começar uma dúvida nova.

O que eu fiz

Fiz o aplicativo inteiro: a interface em Streamlit, as instruções de cada professor (engenharia de prompt), o histórico da conversa e o envio de foto para o modelo.

É um projeto pequeno e sem testes automatizados. Ele mostra a minha motivação com ensino e como eu uso um modelo multimodal.

Classificação de score de crédito

Quem é bom pagador? Deixe os dados responderem.

O problema

Um banco precisa decidir como tratar cada cliente de cartão de crédito, e para isso classifica o score de cada um. Com o histórico de milhares de clientes (renda, atrasos, dívidas, uso do cartão), um modelo de machine learning aprende a classificar o score em três faixas.

Era o projeto final do curso de Data Science da Digital House. O enunciado pedia escolher um problema de machine learning, comparar modelos, ajustar os parâmetros, montar um pipeline, analisar a importância das variáveis, guardar o melhor modelo e apresentar o resultado a um público não técnico.

Como funciona, passo a passo

  1. Os dados. Uma tabela de clientes com 28 colunas, como renda anual, número de cartões, taxa de juros, dias de atraso, dívida em aberto e o score, que é o que queremos prever.
  2. A limpeza. Números gravados como texto foram convertidos, o tempo de histórico de crédito virou meses e os valores extremos (outliers) foram removidos pelo método IQR.
  3. Quais variáveis importam. A equipe mediu a importância de cada variável (com Extra Trees) e usou VIF e PCA para entender as relações entre elas.
  4. Seis modelos disputam. Um modelo de referência, que só repete a classe mais comum, e cinco modelos de verdade: Extra Trees, Random Forest, XGBoost, rede neural (MLP) e um Stacking de XGBoost com SVC. O modelo de referência acerta 54,1% só repetindo a classe mais comum. O Random Forest, o melhor, chega a 77,6% de acurácia, com AUROC de 0,897.
  5. Do notebook ao app. O melhor modelo foi salvo com pickle, e um aplicativo em Streamlit permite testar o modelo com dados novos. Uma apresentação em slides resume o resultado para um público não técnico.

O que eu fiz

Foi um trabalho em grupo de 4 pessoas. A análise e a modelagem no notebook foram feitas pela equipe. A minha contribuição registrada no Git é o aplicativo em Streamlit (CreditScore.py) e o arquivo de dependências.

Logística urbana com microsserviços

Três serviços pequenos, cada um com uma função.

O problema

Uma transportadora precisa saber se as entregas chegam no prazo, quanto custam e quais motoristas se destacam. O projeto simula isso com dados sintéticos (20 motoristas, 12 veículos e 400 entregas) e divide o sistema em três serviços independentes que conversam por HTTP. O objetivo da atividade era mostrar uma arquitetura de microsserviços funcionando de ponta a ponta.

Como funciona, passo a passo

  1. O serviço de dados guarda tudo. Motoristas, veículos e entregas ficam num PostgreSQL, e o serviço oferece uma API para ler e gravar, com paginação e filtros.
  2. O serviço de processamento calcula os indicadores. Ele busca os dados via HTTP e calcula pontualidade, atrasos, custo por km, ranking de motoristas e entregas com custo fora do normal (outliers, pela regra do IQR). Regra de atraso: atraso = máx(0, entregue − prazo). "No prazo" significa atraso zero, e atraso crítico é de 120 minutos ou mais.
  3. O serviço de relatório junta tudo. Ele consulta os dois outros e entrega o relatório em JSON, CSV ou HTML.
  4. Os tempos de espera foram planejados. Cada camada espera mais do que a de baixo leva no pior caso, assim o erro aparece no serviço mais próximo da causa, e não como uma falha confusa lá no topo.
  5. Sobe com um comando. O docker compose up cria o banco e carrega os dados. Os dados vêm de uma semente fixa, então os números são sempre os mesmos.

O que o projeto inclui

Testes por serviço, que rodam sem Docker, rede ou banco (as chamadas são simuladas), um README completo com endpoints, filtros e erros, e um relatório e uma apresentação de 12 slides.

As limitações estão escritas no README: sem autenticação, dados sintéticos, comunicação síncrona e uso didático.
